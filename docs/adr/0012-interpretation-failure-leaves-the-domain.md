# 解读失败逐报告出域，取代三处半成品

Status: Accepted

本仓 ADR **0012**。续 ADR-0011（成因词表与判定入口收敛为服务端单点）。

## Context

ADR-0011 把「一次报告解读为什么失败、还有没有救、患者该做什么」收敛成**一份成因词表、
一个判定入口**，但那一票**没有改响应契约** —— 成因只落在 `parsed_content` 里。于是
「这份报告怎么了」在契约里有**三处半成品**，而它们**都不是**成因：

- `processing_error` —— 一句后端自由文本（`报告智能解读失败，请重新上传或稍后重试。`），
  前端原样显示。它对多类失败是错的。
- `processing_warnings` —— `["文件名: 模型/框架错误原文"]`。它是**拼接串**：把 provider
  的自由文本直接呈现给患者，而那段文本是给排障看的。
- `extraction_job.error_class` —— 出域了，但没有任何前端读者；它的取值是策略标签
  （`ReportExtractionRetryable` / `ReportExtractionFailed`），不是成因。
  另有一个 `parsed_content["error_class"]`（Python 类名）**写入后全仓无人读**。

三个名字，三种形状，没有一个能回答「患者该做什么」。

## Decision

**报告响应新增一个类型化的失败块，取代上述三处。**

```
interpretation_failure: {
  cause:        <五成因词表，派生自 app/service/interpretation_failure.py>
  retryable:    成因的派生读法
  action:       成因的派生读法（upload_again / no_action）
  failed_files: [{ file_index, filename }]
} | null
```

四条边界：

1. **`retryable` 与 `action` 是派生的，不是独立事实。** 服务端算好一起送出去，与
   `AdmissionLedger` 把四类之和一起送出去同一个理由：推导规则只有一处，前端不再按成因表
   推一遍。
2. **失败的文件只带文件名。** `processing_warnings` 的错误原文**不出域** —— 它是给排障
   看的。文件名是患者自己给的，认得出来。
3. **值集靠派生，不靠抄写。** 契约层的 `FAILURE_LITERAL` / `PATIENT_ACTION_LITERAL` 由
   词表派生出（`Literal[*FAILURES_ORDERED]`），与 `AdmissionReasonLiteral` 同一个做法。
   因此词表模块**不得 import 任何项目模块**（否则会把 `vision_encoder` 拖进契约层的导入
   路径）。
4. **空块是诚实的空。** 历史行没有成因 → 读成 `null`，不猜一个。患者侧退回状态级的那句
   话，而不是收到一个编出来的成因。

闸门（确认/评估能不能做）**仍然只由报告状态决定**（#139 已定）；成因只决定闸门被拒时
**那句话**说什么。

### 三条边界（独立评审驳出来的，同一次改动内修掉）

1. **读路径不许因为一个读不懂的字段而 500。** `parsed_content` 是 JSON 列，历史行里
   `failure` 可能是任何形状；一个列表或字典拿去查集合抛 `TypeError: unhashable type`
   —— 患者连打开报告都做不到，而这只是一个我们读不懂的陈旧字段。四个消费点全部先判
   `isinstance(..., str)`。

2. **失败块只描述这一轮。** 失败路径过去写 `{**parsed_content, "failure": ...}`，把上一轮
   解析的**全部**结果一起留下 —— 包括 `file_results`。一次部分解析留下
   `[{"filename": "坏.png", "status": "failed"}]`，下一轮整份材料因**服务不可用**而失败时，
   那份旧结果还在，于是新失败块把「坏.png」列成这一次失败的文件：患者看到一次服务故障
   去归咎于某个文件。`_carried_forward` 只保留抽取轨迹（历史事实，且下一轮可能什么都没
   产生），逐轮结果一律丢掉。`error` 例外 —— 它可能是本轮早些时候（读盘失败）刚写下的
   那句话。

3. **闸门话术不承诺重试。** 闸门在报告还是 `processing`（重试中）与已经 `failed`（次数
   用完）两种时刻都会被拒，同一句话不能对两者都成立。这与前端那条「不承诺」是同一条
   边界，两侧各守一次。

## Alternatives considered

- **保留 `processing_error` 一段时间作为兼容读法。** 改动更小、可回滚，代价是「一次失败
  为什么失败」在契约里同时有两个答案，而四层各写文案的老路仍然活着 —— 这一 PRD 存在的
  理由就是那个多答案状态。**否掉。**

- **把 `extraction_job.error_class` 改名成 `cause` 复用它。** 看起来最省事，实际上是把
  两个不同层级的东西塞进同一个字段：那个字段的取值是**队列策略标签**（要不要重试），
  而成因说的是**坏在哪一环**。一个字段两个含义正是这次要消灭的形状。**否掉。**

- **在失败块里同时给出每个文件的错误原文，让前端自己拼。** 这是 `processing_warnings`
  的老路，也是「第二个入口」的来源。而且错误原文是模型/框架的自由文本，把它呈现给患者
  既没有用也不合适。**否掉。**

- **让失败块也带上「已经自动重试了几次」。** 更透明，但成因就不再是唯一输入 —— 次数是
  队列状态，不是成因。次数由 `extraction_job.attempt_count`（现成字段）在**正在重试**的
  实时提示里给出；终态的话术不承诺「马上会自动重试」（重试次数可能已经用完）。**否掉。**

- **前端继续按 `status === 'failed'` 自己决定说什么。** 那正是今天四层各写一句的来源：
  同一条件两种患者话术，而患者动作永远是「重新上传」。**否掉。**

### 患者侧：一个成因 → 一句话 + 一个颜色 + 一个动作（#230）

前端模块 `frontend/src/interpretationFailure.js` 是**唯一**的患者侧映射之家：成因 →
一句话、一个颜色、一个动作。它取代四层各写一遍的兜底文案（后端一句、`Upload.jsx`
两句、`ReportDetail.jsx` 一句、`reportStatus.js` 一句），并把最后那句「没有成因可给时
说什么」也收进自己 —— 调用点各写一句兜底正是这一票要消灭的形状。

**颜色与状态色是两件事。** 状态色说「这份报告在什么阶段」（`failed` 一律红），成因色
说「这件事有多值得患者动手」。三个「我们这边出的问题」的成因（服务不可用 / 模型不可用
/ 凭据被拒）用 `warning` 而不是 `error`：红色说的是「你上传的东西有问题」，而这一份
材料没问题 —— **这一整票要消灭的正是那个印象**。只有指向患者材料的两个成因是 `error`。

## Consequences

更容易的：

- 四层（worker 日志、审计事件、响应契约、患者文案）说的是同一个成因名。
- 患者侧只做**映射**：一个成因 → 一句话，不再有任何服务端自由文本进入患者界面。
- 新增一类失败会在契约层被**要求取名字**（词表是 `Literal`），而不是在第三个 JSON 键里
  再塞一个字符串。

更难的、被限制了的：

- **`processing_error` / `processing_warnings` / `extraction_job.error_class` 退场是一次
  破坏性契约变更。** 前后端必须一起上；本仓的部署顺序（后端先行、前端随后重建 `dist`）
  让这个窗口存在，但**窗口里前端读不到那三个字段**——它们已经是空值/缺字段，所以前端的
  行为是「退回状态级的那句话」，不是崩。
- **历史行读不出成因**，只能退回状态级的话。这是有意的：不知道就不说知道。
- **成因不再是「一个布尔」**：`retryable` 在契约里是冗余的（可由 `cause` 推出）。留它
  是为了让前端不必实现一遍映射表；代价是同一个事实在契约里出现两次，而两者可能漂。
  防漂的办法是服务端组装时**调用同一个函数**（`is_retryable` / `patient_action`），
  不是各算一遍。
