# 检测页商品由服务端代理读取商城

Status: Accepted

Supersedes in part: 0003（仅就"本仓不得在患者侧展示商品"这一条；0003 关于证据响应
不含商品字段的部分仍然有效，本决定不碰）

本仓 ADR **0005**。genesis-evidence 的 ADR 0004/0006 是**另一个仓库**的记录
（前者是商品推荐能力的由来，后者取代它并把商品权威移到商城）；两个仓各自编号、
互不覆盖，引用时必须带仓库名。

## Context

genesis-evidence 的 ADR 0006 把商品权威整体移到商城，并写明「患者页通过它自己的
服务端代理取商品」。本仓只接了后半句：商品字段随 #173 一并退役之后，本仓不再有任何
取商品的通路，而 `CONTEXT.md` 里「商品」也只剩一句「不属本仓领域内的术语」。

检测页需要图标出商品（genesis-evidence #174），于是这条被 ADR 0006 引用、却从未在
本仓记录过的决定必须先补上——否则「本仓到底准不准碰商品」没有可读的答案。

两个已实测的事实决定了形态：

- **商城网关的 CORS 头组合不合规**：预检响应同时返回 `Access-Control-Allow-Origin: *`
  与 `Access-Control-Allow-Credentials: true`，规范禁止该组合，浏览器会拒绝凭据请求；
  且允许的请求头里不含租户与会话头。**浏览器不得直接调商城。**
- **商城已有面向第三方应用的接入面**（`cloud-mall-api` 的 `modules/webapi`），
  #167 在其上新增了只读商品端点。复用它，不自造协议。

## Decision

**检测页的商品由本服务端读取，前端只与自身同源通信。**

1. **`app/service/mall_goods.py` 是唯一的商城读取通路。** 它负责签名（接入面既有的
   双重 MD5）、超时、响应解析与失败降级。前端通过
   `GET /api/health/report/{id}/recommendations` 读取，浏览器不出现任何商城域名。

2. **可售性由商城过滤，标签交集由本仓做——两件事，不要混为一谈。**
   「这件商品能不能卖」（审核通过 + 已上架 + 租户/门店归属）在商城端点里过滤完；
   「这件商品是否属于该健康方向」是本仓的职责，本仓按标签交集取货。
   genesis 的 ADR 0006 写着「不再叠加第二道过滤」，但它**约束的是 genesis-evidence**
   （该仓不再对商城返回做平台侧审核），与上述标签交集无关，本仓不引用它为自己背书。
   本仓沿用 ADR 0006 的只有两点：商品权威在商城，以及**本仓不做自己的可售性判断**
   （不复制商城的审核/上架过滤）。

   价格以十进制字符串透传（商城返回 `BigDecimal`，转成二进制浮点会抖动）；
   `stock` 为 `null` 表示商城未标注，**不得渲染成 0**。

3. **为空时必须说明是哪一种空，且不得被营销内容填充。** 三种原因互不合并：
   `no_published_card`（本报告没有可据以取货的健康风险，不调商城）、
   `no_label_data`（商城调用成功但按标签交集为空）、
   `mall_unavailable`（不可达/超时/业务错误/凭据未配置）；命中时原因为 `null`。

4. **凭据只从环境注入。** `MALL_WEBAPI_*` 四项齐备才认为已配置；缺任一项即降级为
   「暂无推荐」，**不发一个注定被拒的空密钥请求**——那会把一次配置缺失伪装成一次
   网络故障，而这两种失败对运维的含义完全不同。密钥不进仓库、不进日志。

5. **标签交集是显式的接缝，今天的结果为空，但空由数据产生、不由函数忽略输入产生。**
   `label_pairs_for(condition_code)` 是唯一入口，当前返回空元组——`condition_code →
   (标签名, 取值)` 的映射表是 genesis-evidence 的交付物，本仓只消费不复制（复制必然
   漂移）。交集为空即 `no_label_data`。**不得伪造本地的标签-商品对应关系让它看起来
   是绿的。**

   **（2026-09-30 修订）** 上一版这里写的是「真正的按标签取货需要商城侧给端点加标签
   入参，另行立项」——**那个判断是错的**，因此原文已被本段取代。商城**本来就有**按
   标签取货的接口（`POST /goodsspu/getGoodsByLabels`，入参 `goodsSpuLabels` +
   `returnUnion`，自己做可售性过滤），一行商城代码都不用改。真正缺的从来不是商城
   的入参，而是**我们自己**那份映射表。

   同时纠正另一条：商品的**列表/批量**接口（`/goodsspu/page`、`/goodsspu/ids`）
   **不返回** `goodsSpuLabelList`（恒为 `null`），只有**单品详情** `/goodsspu/{id}`
   带标签。所以"拉一页再在本地按商品标签过滤"这条路走不通——它会静默滤空。有标签
   判据时改为由商城的标签查询给出命中集合；无标签时仍走 #167 的只读端点 +
   `filter_by_labels`（既有已验收行为不变）。

## Alternatives Considered

- **前端直连商城。** 拒绝了——CORS 头组合违规是实测事实，浏览器会拒绝凭据请求；
  且那会让两个系统的展示决策耦合在一个页面里。
- **沿用 0003「本仓不得在患者侧展示商品」的字面。** 拒绝了——它当初拒绝的是"把商品
  引进报告解读链路"，理由是那会让两个系统的展示决策耦合在一个页面里。商品权威整体
  移到商城之后，展示决策只剩商城一方，耦合的前提不成立；继续按字面执行会得到
  「检测页不能有商品」这个谁都不想要的结论。所以 0003 在这一条上被取代，
  在同一段落里写明，而不是留下两条互相矛盾、靠读者猜哪条更新的记录。
- **把商品放回证据响应（`recommendations[]`）。** 拒绝了——这正是 genesis 的 ADR 0006
  退掉的耦合，且商品权威在商城，不在证据服务。
- **本仓缓存/镜像一份商品目录。** 拒绝了——镜像目录是价格与库存的第二个真值来源，
  一定会漂移。
- **无标签时不调商城，直接返回空。** 拒绝了——#174 的验收项字面是「服务端经商城
  端点取货」，早起返回会让这条只剩测试里的 mock，而链路上最易失效的一段
  （凭据、签名、租户绑定）将长期没有真实调用证据。代价是白跑一次，接受。
- **在商城结果之上再加一道平台侧审核闸门。** 拒绝了——商城的可售性过滤已经回答了
  「能不能卖」，再加一道会让「为什么这个商品可见」需要读两个系统的两套审核。
  注意这与第 2 点的标签交集不是一回事：标签交集回答的是「属不属于这个健康方向」，
  商城今天不回答这个问题。

## Consequences

- **可用性依赖商城。** 商城不可达时检测页降级为「暂无推荐」而非报错；这是刻意的，
  也是 #174 的验收项之一。
- **`shopId` 存在于返回项中但今天未用于过滤。** 实测同一租户返回了多个门店的商品，
  而本仓没有「当前门店」这个身份——它属于商城会话，不在本仓。按门店收窄要等那条
  身份通路，另行立项；在那之前商城返回什么就展示什么。
- **「标签数据到位后需复验」是一条**未通过**的 QA 用例**，与本决定同时交付；
  它不会因为本仓的实现而变绿。
- **#175 的加购深链不在本决定范围内。** 本决定只覆盖「读到并展示商品」；
  本仓不写商城状态、不自建购物车这一条对两者同样成立。
