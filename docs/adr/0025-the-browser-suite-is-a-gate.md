# 25. 浏览器套件是门禁的一部分 —— 它是唯一关于「看到什么」的自动断言

日期：2026-10-23
状态：已采纳
影响版本：`.github/workflows/ci.yml`（新增两个步骤）；不改任何测试、不改运行时代码

## 背景

`frontend/e2e/` 下有 **81 条** Playwright 用例。配置完整（一次性 SQLite、假后端、
显式覆盖 `.env`），本地能跑，浏览器已装 —— **但没有任何 CI 跑过它们**。

同期实测（2026-10-23，开发机）：81 passed in 55.7 s，连跑第二次 54.0 s，无 flaky。

## 决定

接进 CI，作为 `verify` job 里 `Run tests` 之后的独立步骤。

## 为什么它们是门禁而不是「可选证据」

本仓其余测试都是 Python，**只能证明 API 说对了什么**。一次全绿的 `pytest`
完全相容于「前端把 failed 渲染成和 passed 同色」。

这不是假设：那条 spec 的名字就是实证 ——
`failed 报告在历史列表与详情页同色同说法`。它存在，是因为那件事发生过。
同类还有 `定位缺失时如实说明「无原文定位」，不猜第 1 页`。

「患者看到什么」是本仓的产品边界。没有一条自动断言守它，等于让这部分
只能靠人看 —— 而人不会在每次 PR 上看 81 个页面。

## 被否的方案

- **不接，继续只靠 `verify-healthflow` skill。** 那是按需的、人触发的，
  与本仓已有的纪律一致（`docs/adr/0021` 说验证按风险成形）。它输在
  **这 81 条已经是自动化断言了**：不接不是「省下」，而是让已有的断言永远沉默。
  风险成形说的是「不要为低风险路径造新测试」，不是「造好了不要跑」。

- **并进 `Run tests` 那一步。** 少一个步骤、少一份日志。它输在**红了看不出原因**：
  同一条红既可能是 API 契约破了，也可能是页面渲染破了，而这两件事的修法完全不同。

- **只在 main 上跑（PR 不跑）。** 便宜。它输在**它要防的东西发生在这里**：
  颜色与措辞是 PR 改的，等合进 main 再红，改的人已经走了。

## 后果

- 每个 PR 多约 55 s（外加 chromium 下载，有缓存）。
- 失败时会附 `playwright-report/` 与 `test-results/`（`if: always()`，留 7 天）——
  一份只有测试名的失败清单，修不动。
- 前端构建是这 81 条的前置（`playwright.config.js` 用 `frontend/dist`），
  而 CI 在 `Run tests` 之前已经构建过，所以顺序是有意的，不是巧合。

## 未做

e2e 没有接**并行**（Playwright 默认按文件并行，当前配置未调）。
81 条 55 s 还在可接受区间；若将来变慢，那是第一步要动的地方。
