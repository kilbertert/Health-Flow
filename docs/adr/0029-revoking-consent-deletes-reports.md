# 29. 撤回解读同意就是删除：一次提交里删库，提交之后再删文件

日期：2026-10-27
Status: Accepted

本仓 ADR **0029**。它落地 ADR 0026 第 5 条的最后一句（「撤回解读同意时删除该主体的全部
报告」）与 ADR 0027 的「未做的」第二条；两条记录都仍然有效，本记录不推翻它们的任何结论，
只回答三件事：**删什么**、**什么时候删文件**、**留证长什么样**。

## Context

撤回「报告解读」同意必须真的把数据删掉，否则撤回是一句空话。落地时有三个问题没有现成
答案，而每一个都有一个走上去更省事、事后却无法辩解的形态：

- **审计事件留不留。** PRD 原文写「撤回时删除报告、保留审计事件」。实际数据形状是
  `ReportAuditEvent.report_id` 对报告的**非空外键**、随报告级联；而审计行能追溯到主体，
  属于个人信息。
- **先删库还是先删文件。** 两处删除（单份、按主体）如果各写一遍，其中一份迟早会漂，
  而漂丢的那一半正是「报告行指向一个不存在的文件」。
- **撤回记录怎么回答「这次删了多少」。** 报告行已经没了，`GET /api/auth/reports` 只会
  说零份；而合规要举证的是**这次撤回**的规模。

## Decision

1. **审计事件随报告一起删除，留证由撤回记录承担。** PRD 的那句话按票面的订正执行（已与
   需求方确认）：保留审计事件既要改表结构（非空外键），又与「删除请求」本身相反 ——
   一张能追到我的审计表不是「保留记录」，是「没删干净」。撤回那条同意记录自己写着删掉
   了多少份，那才是这次操作的证据。

2. **删除只有一条路径，两种规模共用。** `app/service/report_deletion.py` 的
   `delete_reports`：删报告行，flush，返回一个 `Deletion` 句柄；`Deletion.commit(db)` 提交
   **成功之后**才删磁盘文件、再收掉空目录。单份删除（`DELETE /report/{id}`）与撤回收敛到
   同一条路径上 —— 顺序这件事有两份实现就一定有一份会漂。

3. **撤回记录与删除进同一次提交。** `consent.record_consent` 在写 `revoked` 行的那一次
   调用里发出删除，路由用 `consent.commit_consent` 提交（有句柄走句柄，没有就 `db.commit()`）。
   两条事实要么同时成立（记录说删了 N 份、报告也确实不在了），要么都不成立。

4. **`deleted_report_count` 只在「删报告的撤回」上有值。** 授予、撤回「商品推荐」、从未表态
   都是 `NULL` —— 「这一项撤回不涉及报告」与「这一项撤回删了 0 份报告」是两件事，后者是
   一个会被读错的值。报告数为零时写 `0`：那是一次真实的「一份也没删」。

5. **文件删不掉不把删除判成失败。** 数据库已经提交，报告不属于患者了；`unlink` 失败只记
   一条日志，残留字节由运维侧的保留策略清扫。判成失败会让患者反复重试一件已经完成的事，
   而「数据库里没有、磁盘上还有」在这里不是半删状态 —— 没有任何一行指向那个文件。

6. **不动「商品推荐」那一项、不动同意记录本身。** 撤回推荐只停止推荐；`health_data_consents`
   依旧只追加，撤回是又一行，此前的行一个字段都没有被改写（ADR 0027 的第 1 条）。

7. **撤回与上传之间不留窗口。** 上传的同意判定在请求进来时做一次，而撤回可能落在
   判定与写入之间：撤回事务删掉当时的全部报告（那次上传自己的行还没提交，删不到），
   随后这次写入落地 —— 一次已经撤回的授权下多出一份新报告。理由已问过一次，所以把
   判定与写入收进同一写事务：`db.commit()` **之前**再问同一条判据（`consent.has_valid`），
   不等就回滚，并删掉这次上传已经写下的原始文件。判据仍只有一处。拒绝时返回 403 与
   `report_interpretation_consent_required`，与第一道闸门同一个结论。代价是一次上传
   多读一次同意表，以及那条共用的「删掉刚落的文件」路径。

## 被否掉的替代形态

**保留审计事件（PRD 原文）。**
最强的理由：删除请求不该把「发生过什么」也删掉。审计是离线留证，保留它能让「他在什么时候
同意过、上传过几份」在数据删除之后仍然可查，也没有人会因为一张内部审计表而觉得健康数据
还在。这听起来正是合规想要的东西。

它输在**它留的是一份可以个人的记录**。审计行有 `report_id`（对报告的非空外键）、`actor`
（主体标识）、`detail`（文件名与计数）。它不是一份脱敏日志，而是一张能回到某个患者的表；
把它留着，等于患者撤回之后我们仍然保存着「他做过什么」。要让保留成立，就得改表结构（外键
改成可空）、再论证剩下的字段确实不含可识别内容 —— 而 PRD 的测试要求恰恰是「审计事件全
部不存在」。所以按票面的订正删除，留证换到撤回记录上：它回答规模与时刻，不回答内容。

**先删文件、后删库。**
最强的理由：先让字节消失最安全 —— 即使事务失败，磁盘上也没有患者数据了，而数据里最敏感的
就是文件本身。

它输在失败之后留下的形状。事务回滚时报告行还在、文件已经不在：患者看到一份打不开也删不掉
的报告，而每次重试都会再删一次已经不在的文件。这个方向在本仓已经被单份删除选定过（「先删
数据库主记录；向量索引是尽力而为，放在 DB 成功之后」），本记录只是把它变成唯一实现，并补上
「提交成功之后才删」这一条 —— 原实现是在 `db.commit()` 之后删，形状正确，但没有把「提交」
与「删文件」绑在一个对象上，第二个调用方很容易只记得第一步。

**把「要不要删报告」交给路由判断。**
最强的理由：路由最清楚患者点了哪一项、表了什么态；在 `record_consent` 里判断「哪一项撤回
会删报告」等于把一个产品规则塞进合规记录的写入器。

它输在**调用方会漏**。删除的后果与那条记录必须是同一次提交，而任何一个新的写入通道
（种子、将来的后台工具）都得自己重新实现「写撤回 + 删报告 + 先库后文件」。规则放进
`record_consent` 的同一处，新通道只需要调它。

## Consequences

**更容易的：**

- 撤回的后果由一次提交兑现：「删了 N 份」与被删掉的 N 份报告同生共死，不会出现一边成立。
- 单份删除与按主体删除共用一条路径，顺序只有一处可以改错。
- 报告列表在撤回后直接为空（HTTP 层与浏览器都断言过），而不是挂着打不开的行。

**更难的、被限制了的：**

- **删除是同步的**，在撤回那次请求里跑完。一个主体有几百份报告时，撤回会变成一个长请求；
  这是当前规模下的刻意选择，代价写在测试里（一次删除全部报告），没有队列。
- **`deleted_report_count` 是快照，不是可重建的计数。** 报告行删掉之后，没有任何东西能
  复核这个数；它只能被相信。这是「报告已经不存在」的必然结果，而不是一个遗漏。
- **同意记录只增不减**（ADR 0027 的代价在这里第一次真正付出）：撤回记录、以及此前所有授予
  记录，都在删除之后保留下来，且它们含主体标识。保留策略仍是一个需要单独回答的问题。
- **审计事件不再能回答「这份报告曾经存在过」**：那正是本记录选择的代价，换来的是删除请求
  被真正执行。

## 未做的

- 「隐私与授权」页面与二次确认：在商城 H5 模块里，不在本仓（PRD #266）。
- 删除的异步化与进度：当前规模不需要，没有做。
- 同意记录（含主体标识）的保留期：ADR 0027 已经把它标成需要一条明确策略的问题，本记录
  不改变那个状态。
