# 19. 契约暴露的封闭取值集只能有一位主人

日期：2026-10-17
状态：已采纳
影响版本：本仓库（`tests/test_contract_vocabulary_ownership.py`、`app/schema/report.py`、
`app/service/report_subject.py`）

## 背景

#245 / #246 / #247 是**同一个类**的三个实例：一个领域事实的含义，由「恰好写了它的那段
代码」携带，而不是由一份所有生产者与消费者共享的声明携带。

修掉这三处症状之后，那个类仍然是**无界的**：没有任何机械判据能发现新成员，只能靠每天
一次的 architecture-review agent 去读代码。三个 issue 各自还在 Out of Scope 里列着同类
候补（抽取队列状态词表、`{"confirmed","assessed"}` 业务组合、前端生效值回退链、前端主体
一致性闸门）。

本仓已有的守卫是**一次一个概念手写**的：`test_report_status_vocabulary.py` 扫状态字面量、
`test_admission.py::test_no_second_vocabulary_is_declared_anywhere` 扫原因名。它们的
**覆盖面等于「有人想起来写了一份」** —— 这就是这一类会反复长出来的机制。

## 决定

**一条按结构判、不按名字判的机械不变式：同一个封闭取值集不得被两个文件各声明一次。**

- 判据：`app/` 下每一处**全字面量**的 `Literal[...]`，按取值元组聚合；同一个取值集出现在
  **一个以上文件**即违规。派生写法（`Literal[*X]`）不算声明 —— 它正是本规则要求的形状。
- 例外必须逐条写下理由（`EXEMPT`），理由是「这不是本仓的决定」那一类。当前是空集。
- 词表之家自身也不得重复声明同一组取值（自己跟自己漂移同样是漂移）。

## 为什么按「跨文件」划界，而不是「契约里出现的每个 Literal」

这条界线是**量出来的**：

- `app/schema/evidence.py` 里有 6 组重复取值（`routine/soon/urgent/emergency`、
  `context_only`、`not_available`、`high/moderate/low/very_low[/mixed]`、
  `体检报告解读与健康风险提示`），但它们**全在同一个文件里**，而且**服务端从不分支**于其中
  任何取值 —— `grep` 在 `app/service` 与 `app/api` 下对它们零命中。它们是**上游证据服务的
  线路格式**在逐个模型边界上的复述。给它们指定一个「家」，等于宣称服务端拥有一项它并不
  拥有的决定 —— 那会造出一种**假的所有权**，比重复更糟。
- 真正跨边界重复、且服务端**确实分支**于其取值的是另外两组：报告状态
  （`schema/report.py:247` ↔ `service/report_status.py:21`）与报告主体一致性
  （`schema/report.py:250,296` ↔ `service/report_subject.py:20`）。这两组是这条不变式
  抓到的、也是它要抓的。

换句话说：判据是「同一个封闭取值集被两个文件各声明一次」。「契约里有字面量」会把上游
线路格式判红，而那种红只会教人给不属于自己的东西编一个家。

## 被否掉的方案

- **把 `app/schema/evidence.py` 里那 6 组也收敛掉（新建一个「证据响应词表」之家）。** 看起来
  更彻底。它输在**服务端不拥有那些取值**：那是上游证据服务的线路格式，本仓只是逐个边界
  复述它。给它们指定一个家会宣称一项不存在的决定，而下一个读代码的人会以为本仓可以
  决定 `urgency` 有哪几种取值。**重复与所有权是两件事，本记录只治后者。**
- **按名字判（「凡名字里有 vocabulary 的模块就是词表之家」）。** 会让本不变式在
  `report_status.py` / `report_subject.py` 上失明 —— 而那正是它最初抓到的两组。
  名字是约定，结构才是判据。
- **继续一次一个概念手写守卫。** 那是现状，也是三个 issue 被 agent 读出来的原因。
  一条机械判据胜过三份追认。
- **把两条既有的手写守卫删掉，只留这一条。** 它们各有本规则不覆盖的部分
  （状态字面量扫描还管「拼错的近似名」，原因名扫描还管子集与并集的恒等）。三者互补。

## 后果

更容易的：

- 下一个同类概念长出来时，这条规则**自己会红** —— 不必等 agent 读代码、不必等三个 issue
  中的某一个被提起。
- 契约里的取值集从此只能是「一份声明的投影」，读者不必再问「这两个 `Literal` 是同一个
  概念吗」。

更难的、被限制了的：

- **契约里再写一个全字面量的 `Literal` 会在两个文件同时出现时失败。** 想加一组新的封闭
  取值，就必须先在 service 层给它一个家 —— 那正是这条规则想要的摩擦。
- **它不判「该不该有这个家」。** 一个取值集可以每个文件都老老实实派生自同一个空壳模块，
  而那个模块没有任何判定逻辑。这条规则只保证「只有一位主人」，不保证那位主人真的持有决定。
- **上游线路格式那一类继续重复**，且本记录明确把它们排除在外。这是刻意的（见被否掉的
  第一种方案），代价是读者要能分辨「6 组重复是线路格式、2 组重复是所有权」——本记录就是
  那个说明的地方。
- 它按 AST 判，因此只覆盖 Python；前端的取值集由各概念的跨语言断言（`test_mall_goods`、
  `test_frontend_*`）覆盖，不在这条规则里。

## 验证

| 断言 | 结果 |
| --- | --- |
| 改前（`main`）跑本规则 | 抓到 2 组：状态（`schema:247` ↔ `report_status:21`）、主体一致性（`schema:250,296` ↔ `report_subject:20`） |
| 改后 | 绿（两组都改为 `Literal[*X]` 派生） |
| 上游线路格式那 6 组 | 不报（同文件；且服务端零分支） |
| 词表之家自身 | 7 个模块各只声明一次自己那组取值 |
