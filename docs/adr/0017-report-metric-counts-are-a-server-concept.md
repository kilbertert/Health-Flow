# 17. 报告指标计数是服务端的一个概念，结论句以「有没有没判出来的行」为前提

日期：2026-10-17
状态：已采纳
影响版本：本仓库（`app/service/report_metric_counts.py`、`app/api/auth.py`、
`app/api/report.py`、`app/schema/auth.py`、`app/schema/report.py`、
`frontend/src/pages/ReportDetail.jsx`、`frontend/src/pages/Upload.jsx`）

## 背景

「这份报告有多少项指标、其中有几项是异常的、有几项要患者处理」是患者界面上重复出现的
一句话，而它由**三处各自计算的计数**回答，判据互不同步：

| 位置 | 谓词 |
| --- | --- |
| 历史摘要（`app/api/auth.py`） | 判定为 `{H, L, A}` 的行 |
| 报告单总览（`ReportDetail.jsx`） | `isAbnormal(displayFlag(...))`，且先剔掉 `excluded` 行 |
| 确认页页头（`Upload.jsx`） | 另一个谓词 `needsReview`，**把「待核对」也算进去** |

前两者不同源（`isAbnormal` 只认 `{H,L,A}`／`*`），后两者相差整整一个取值。于是同一份
报告在报告单上说「未见异常指标」并给出结论句「当前报告的指标均在参考区间内」，在确认页
上却在数「其中 1 项需要确认」。

**这不是理论分歧，是一条可达的行。** 模型标了 `H`、而值是一个解析不出单值的行
（`3.39 / 3.63`，`two_values`）：`inferred_abnormal_flag` 为空、`displayFlag` 落「待核对」。
这一行不计入历史摘要、不计入报告单的「异常指标 N 项」（它还会把 `abnormalMetrics.length`
压到 0，于是报告单**印出一句假话**），却计入确认页的「其中 N 项需要确认」。

**第三个数**：「N 项指标」在三处指的也不是同一批行 —— 历史摘要与确认页数全部已解析行，
报告单的表格与分页数排除 `excluded` 之后的行。患者排除一条之后，同一份报告的历史列表与
报告单会给出两个「N」。

**删除测试**：删掉 `_abnormal_metric_count` → 历史摘要没有数字；删掉 `ReportDetail` 的
`abnormalMetrics` → 报告单的告警没有数字**也没有名字列表**；删掉 `needsReview` 的计数用法
→ 确认页页头没有数字。三处各自承重、互不引用 —— 这正是「这个概念没有家」的形状。

## 决定

**「报告指标计数」是服务端拥有的单一领域概念：每个数各有唯一判据，由服务端算好随响应
出域，患者侧只渲染。**

1. **五个数，各有具名判据**（`app/service/report_metric_counts.py`，全仓库唯一产生处）：
   `parsed`（已解析行数，分母）、`abnormal`（判定为 `H`/`L`/`A`）、`needs_review`（异常，
   或判定不出来但模型宣称异常）、`undecided`（判定为空且患者没有排除）、`in_range`
   （判定为 `N` 且患者没有排除，#270）。
2. **`needs_review` 与 `undecided` 刻意是两个数。** 一行「一行两个值」同时落进两桶；
   一行「模型没标异常、也没有参考范围」只落进 `undecided`。并成一个数会让结论句重新有机会
   说谎。
3. **`abnormal`、`in_range`、`undecided` 是同一份判定的三个互斥出口。** 判定返回
   `H`/`L`/`A` 落第一个，返回 `N` 落第二个，返回空落第三个 —— 三者两两不相交，且
   `abnormal + in_range + undecided == parsed - 被排除的行数`。因此 `in_range`
   **不得由减法得出**：`parsed - abnormal - undecided` 会把患者排除的行算成正常，而
   患者说的是「这一行不要解读」。
4. **`abnormal` 与 `needs_review` 是两个具名事实，不是一个数的两套算法。** 若某份报告上
   它们不同，那是两个事实的差 —— 契约上是两个字段。
5. **一处出域。** 两个计数接口都带同一份计数块：`ReportHistoryItem` 增
   `needs_review_count` 与 `in_range`；`MedicalReportResponse` 增 `counts`。
   `in_range` 在两个契约里**同名**（历史条目没有 `*_count` 后缀），因为患者侧要跨这两个
   契约对同一个数 —— 两处不同名就得在模块里翻译一次键名，而翻译点就是下一次漂移点。
6. **患者侧只渲染。** `ReportDetail.jsx` 与 `Upload.jsx` 的**计数**改为读服务端字段；
   `displayFlag` / `isAbnormal` / `needsReview` 保留为**纯展示映射**（行高亮、标签、
   显示哪些行、名字列表）。删除的是「客户端算数」，不是「客户端显示」。
7. **结论句不越界。** 报告单在「异常行数 == 0」时说的话，与「有没有未判定的行」一致 ——
   **不得**在存在未判定行时宣告「当前报告的指标均在参考区间内」。这是本改动可见的行为
   变化。

## 被否掉的方案

- **只把前端那个谓词改成和服务端一样的 `isAbnormal(displayFlag(...))`。** 这是最小改动，
  能让报告单与历史摘要同口径。它输在三处仍然各自算数：确认页那个把「待核对」也算进去的
  计数依旧不同源，而「这一份报告有几项要处理」仍然没有家 —— 下一次新增一种准入结论，
  三处会再次各自漂移（#245 的 User Story 4 说的正是这件事）。
- **把 `undecided` 并进 `needs_review`。** 少一个字段、少一个概念。代价是结论句失去前提：
  报告单要么继续在有未判定行时说「均在参考区间内」（本记录要消灭的假话），要么在患者
  什么都做不了的行上也请他处理一次（那一类没有「待核对」可显示）。
- **让前端继续算、只是把判据集中到 `admissionText.js` 一处。** 这是「前端单点」，比现在好；
  但它把「这一份报告有几个数」这件事留在了浏览器里 —— 而历史摘要那个数天生在服务端
  （列表接口不返回逐行指标），于是同一个概念必然横跨两种语言，两侧判据迟早分叉。
- **改「N 项指标」的口径时把 `excluded` 的行从报告单表格里删掉，或反过来让历史摘要也
  不数它们。** 两者都改动了患者已经看到过的语义。本记录只收「计数从哪里来」，
  `excluded` 的行为（不进报告单总览）保持原样。

## 后果

更容易的：

- 历史摘要、报告单、确认页对同一份报告说同一个数；新增一种准入结论不会再让三处漂移。
- 报告单不再在有一行没判出来的时候说「均在参考区间内」。
- `needs_review` 成为一个**具名**的患者动作口径：确认页页头那句「其中 N 项需要确认」
  从此有唯一来源。

### 两条自查改正（同一次改动内修掉）

第一版提交之后自查逮到两条，都是这条改动自己引入的。记在这里因为它们各自是一条**边界**：

1. **`needs_review` 必须逐字镜像前端的 `displayFlag`，而不只是「模型宣称异常」。**
   第一版漏了**判不出来、患者还没表态**的行（值、参考范围都齐，只差他核对）—— 前端
   `displayFlag` 把那一类显示成「待核对」并计进页头那个数，而服务端没算。于是页头可能
   站在一个**比它实际列出的行更少**的数字上（数字说 2 项，列表里有 3 条）。
   现在 `displays_as_review()` 是 `displayFlag` + `admissionText.admissionBeforeAssessment`
   四条分支的服务端镜像，等价性由测试**驱动真实 `displayFlag` 逐行比对**（先例
   `tests/test_two_value_agreement.py`），并在用例里留了那条分界行作负控。

2. **`undecided` 与 `needs_review` 是两个问题，不能合并。** 改正 1 时一度把二者并成
   一个判据，随即发现自己错了：`undecided` 说的是「我们给出判定了吗」（关于判定的**事实**，
   驱动结论句），`needs_review` 说的是「页面上会请他看一眼吗」（关于显示的**镜像**，
   驱动页头）。两者在「患者已表态、模型没标异常、又判不出来」这一类上**必然分开** ——
   并成一个数，就会在「页头诚实」与「结论句诚实」之间二选一。

3. **少了 `counts` 字段时不替服务端断言。** 旧响应（或无该字段的夹具）里前端推不出
   `undecided`（它要「判定为空」与「患者没排除」两条，而前端那份展示映射对「模型没标异常、
   也没有参考范围」的行无法与「判不了」区分）。第一版回落成「当前报告的指标均在参考区间内」，
   那是**替服务端说一句它没说过的话**。改为如实说「未发现异常标记的指标」。

更难的、被限制了的：

- **契约多了三个字段**（`ReportHistoryItem.needs_review_count`、`ReportHistoryItem.in_range`、
  `MedicalReportResponse.counts`）。旧响应没有它们时前端回落到本地计数，所以这是向后兼容的，
  但回落路径存在本身是债务：它保证前端**永远**有一份可以偷偷算数的退路。
- **`in_range` 多了一条要维持的等式**：`abnormal + in_range + undecided == parsed - 排除行`。
  它是三个数的自洽约束，对新加入的判据（例如「需监控」那一档，本 PRD 明确不存在）是
  一道闸：新增一档而不更新等式，`tests/test_auth` 的断言会先红。
- **`undecided` 是一个新的、需要被记住的概念。** 它不是准入结论（准入对可判的未核对行说
  `awaiting_confirmation`），也不等于「需要患者处理」。把三者混起来是本记录要防止的下一次
  退化。
- **报告单的结论句变短了一类**：有未判定行时它现在说「另有 N 项未能判定」，而不再给出一句
  让人放心的结论。这是刻意的 —— 那句话此前是假的。
- 计数与**闸门**仍是两件事：报告单的告警是展示，闸门由报告状态决定，本记录不把它搬回闸门。

## 验证

| 断言 | 结果 |
| --- | --- |

| 结论句 | 有未判定行时**不**出现「均在参考区间内」，改说「另有 N 项未能判定」（node 驱动真实 `ReportDetail.jsx`） |
