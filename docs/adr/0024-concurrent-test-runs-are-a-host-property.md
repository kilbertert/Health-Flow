# 24. 同时能跑几次测试，是主机的属性，不是仓库的

日期：2026-10-23
状态：已采纳
影响版本：`tests/conftest.py`（新增）；不改任何运行时代码、不改任何测试断言

## 背景

2026-10-23，同一台开发机上开了多个 Claude Code 会话，同时跑全量测试：

- **7 个 pytest 进程**
- load average **5.28 → 79**
- `sshd` 与 `tailscaled` 抢不到 CPU，tailnet 掉线
- **管理这台机器的通道本身消失** —— 不是变慢，是不可达

本仓全量串行 255 s。7 个并发就是 7 × 255 s 的 CPU 需求挤在 8 个核上。

## 决定

在 `tests/conftest.py` 里加一个 **主机级 flock 槽位**，默认 2 个。

它限制的是**同时存在几次跑**，与「一次跑多宽」是正交的两个轴：

| 轴 | 谁管 |
|---|---|
| 一次跑多宽 | `addopts` 的 `-n`（本仓默认串行，无 xdist） |
| 同时几次跑 | 本文件的槽位 |

## 三个判据，每个都对应一种会静默失效的写法

1. **按主机分，不按 checkout 或仓库分。** 被耗尽的是核，而核是共享的。
   AI-Ops 的第一版按 checkout root 分锁，理由是「worktree 之间不共享 venv」——
   但事故恰恰是**不同 worktree** 的会话：每把锁互不相干，一个都没排队。
   槽位文件名 `host-test-slot-N.lock` 因此**不带仓库名**：三个仓同时跑，
   耗尽的是同一台机器。

2. **不按 `-n` 判。** AI-Ops 只在多 worker 时占槽，因为那边默认 `-n 4`。
   本仓默认没有 xdist，**每一次跑都是串行**；照抄那个判据会让闸门完全失效
   （实测：外部占满两个槽，pytest 仍在 4 s 内跑完）。
   串行跑一样吃一个核 —— 七个串行会话就是七个核。

3. **等待有上限。** `WAIT_SECONDS` 到点抛 `UsageError`，不永远等。
   AI-Ops 的第一版死锁过（xdist worker 也抢同一把锁），两个并发跑到被 kill
   为止没有任何输出；一个静默挂住比一个明确的失败更贵。

## 被否的方案

- **按仓库各配一份槽位。** 看起来更宽容。它输在**算错了被争抢的资源**：
  三个仓各 2 槽 = 主机上 6 个槽，等于没有上限，而且从任何单个仓都看不出来。

- **放进共享包或 pytest 插件。** 最干净。做不到：pytest 只保证加载**仓内**的
  `conftest.py`，没有一个三仓都加载的安装点。所以规则复制三份，
  注释里互相指认——**两个必须一致的文件，胜过一个没人加载的钩子**。

- **只在 CI 上限制。** 搞错了谁在付钱：CI 一次 PR 跑一次；事故发生在开发机上，
  且是多个交互会话叠加。

## 后果

- 全量测试在并发会话下会排队。这是有意的：排队比不可达好。
- 单文件快速迭代受的影响可以接受（槽位是文件锁，只在真的有两个跑在飞时才等）。
- 三份副本必须保持一致；`host-test-slot-N.lock` 这个命名是它们唯一的契约，
  改一处不改另两处，上限就静默不再相加。

## 未做

槽位只限制**本仓**的 pytest 进程。`npm` 构建、`ruff`、agent 自己的推理
都不经过这个闸门——它们由别的机制（或没有机制）限制。
