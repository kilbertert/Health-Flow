# 18. 「取货为空的原因」由服务端具名，客户端不再自造一个不存在的取值

日期：2026-10-17
状态：已采纳
影响版本：本仓库（`app/service/recommendation_empty_reason.py`、`app/api/deps.py`、
`app/api/report.py`、`app/api/auth.py`、`app/schema/report.py`、
`frontend/src/api.js`、`frontend/src/components/Recommendations.jsx`）

> **（2026-10-27 加注，决定不变）** 本记录决定「成因由服务端具名、患者侧只映射」，
> 这一条不变。变了的是 `session_expired` 的**患者侧动作**：患者界面迁入商城 H5 之后，
> 客户端先静默换一张新令牌并重试一次，只有商城登录本身也失效时才去商城登录；它不再是
> 一句「重新进入」。另有一组取值将在该模块上线时增加（取货为空里的「未同意」）。
> 见 `docs/adr/0026-patient-ui-moves-into-mall-h5.md`。

## 背景

「本次推荐为什么是空的」在本仓有**四份**答案，三份在服务端、一份只在浏览器里：

- **服务端契约只认三种**：`no_published_card`、`no_label_data`、`mall_unavailable`。
  ADR-0005 第 3 点点名要求「为空时必须说明是哪一种空」。
- **客户端自造了第四种 `session_expired`**，并从**人话字符串**里用正则把它捞出来：
  `const expired = /\b(401|404)\b/.test(err.message || '')`。那条错误信息由 `api.js` 的
  `parseError` 拼成 —— 它把 HTTP 状态压成一句 `请求失败（HTTP 404）`，或**被服务端的
  `detail` 覆盖**。于是这个正则的命中与否取决于**服务端那句话里有没有恰好出现 3 位数字**，
  而不是取决于发生了什么：`detail` 一旦写得更具体，「同一个 401」在有的路径上被认成
  「登录失效」、在有的路径上被认成「商城暂时不可用」——归因**静默翻转**。
- **同一个组件还伪造了一个服务端原因**：`reportId` 为空时直接 `reason: 'no_published_card'`
  —— 报告都还没打开，谈不上「没有风险」。
- **加购失败时，服务端已经给出的原因被丢掉**：`CartLinkResponse(url=None, reason=
  "report_not_ready"|"link_unavailable")` 出域了，而 `addToCart` 只看 `link.url`；
  `url` 为空时一律说「暂时无法跳转到商城」。

而且 `session_expired` **根本不在服务端契约里**（`RecommendationReason` 是封闭的
`Literal`）—— 它既不会被单独出域，也不会被契约测试看见。本仓**没有登录页**（#172 之后
自助登录整体退役），可那句话却叫患者「重新登录」：同一个事实，患者侧两句话，其中一句
指向一个不存在的入口。

这与 #226 已经消灭的「按自由文本子串嗅探决定重试」是**同一形状的错法**，只是换了一层。
ADR-0005 把这个概念**写进了 ADR** 却没有写进一个模块，于是服务端点内联判定、
`app/service/mall_goods.py` 再声明一份子集、前端自造第三种口径。

## 决定

**「取货为空的原因」是一个服务端拥有的领域概念：一次取货或加购为什么没有给出东西，是
服务端判定的、逐请求出域的具名结论；患者侧只映射成一句话，且不存在客户端能产生而服务端
产生不了的原因。**

1. **一份词表、三组取值**（`app/service/recommendation_empty_reason.py`，全仓库唯一的家）：
   取货为空三种、加购为空两种、报告访问失败两种。三组两两不相交 —— 它们回答三个不同的
   问题（有没有货 / 能不能跳过去 / 这份报告读不读得到）。
2. **出域契约与商城子集都从它派生**：`RecommendationReason`、`CartLinkResponse.reason`、
   `mall_goods.Reason` 都是 `Literal[*...]`，不再是各自抄一遍的字面量。
3. **报告访问失败由服务端具名。** 401/404 的成因随响应头
   `X-Report-Access-Reason` 出域（`session_expired` / `report_not_found`）；`detail` 那句
   人话保持人类可读，两者各自为本。`parseError` 把状态码与成因**一起**交给调用方 ——
   此前它只留下那句话，状态码被丢掉，于是调用方只能从文本里把它嗅探回来。
4. **销毁客户端自造的原因。** `session_expired` 的**自造**分支与正则嗅探删除；取值本身
   保留，改由服务端给出。会话失效那句措辞必须是「请从商城入口重新进入」——与
   `app/api/auth.py` 同向，**不得**出现「登录」。
5. **加购失败读服务端的 `reason`。** `report_not_ready` 与 `link_unavailable` 各是一句话，
   删掉那句一概而论的「暂时无法跳转到商城」。
6. **删除前端投影。** `!reportId` 不再伪造 `no_published_card`；组件在那个状态下如实说
   「还没有报告」，不冒充服务端成因。

7. **一次都没发出时，「没货」与「没问成」仍然分开。** 按健康问题分组后，没有标签映射的
   方向不发取货（那是对的）；但若商城凭据未配置，一次调用都没有时也必须说
   `mall_unavailable` 而不是 `no_label_data` —— 前者是「我们没问成」，后者是「商城说没货」，
   而凭据缺失不依赖任何调用即可回答。改动前这里把空标签集交给一次调用，它会在发请求
   之前就回答 `mall_unavailable`；分组不能把这个归因丢掉。只认**可判定**的这一种：
   一个请求都没发出时，真正的网络不可达无从观测，不猜它。

## 被否掉的方案

- **让前端改读 `res.status`（把结构化的状态码留下来），不加响应头。** 这是最小改动，也确实
  消灭了「按文本嗅探」。它输在两处：① 状态与成因不是一对一 —— 401 与 404 只是**今天**
  刚好一一对应，而「成因」是领域事实、「状态码」是传输细节，把领域结论建立在状态码上会
  让下一次调整状态（比如把某个 403 也归入访问失败）变成一次跨语言的隐式约定变更；
  ② 加购那条路的成因（`report_not_ready` / `link_unavailable`）根本不在 HTTP 状态里，
  它只在响应体里 —— 两条路需要两种机制，而两种机制就是两个家。
- **只把 `session_expired` 加进服务端词表，判据仍由前端从文本里取。** 更小，但保留了
  整条错法：归因仍取决于服务端那句话的措辞，`detail` 一改就静默翻转。ADR-0011 的
  Alternatives 里那句「再补几个词是一个永远追不上的动作」在这里逐字成立。
- **前端保留兜底，只是把「商城不可用」换成一句中性的话。** 中性的话在四类成因上都成立，
  于是它也**什么信息都没给**——而 ADR-0005 第 3 点要求的正是「必须说明是哪一种空」。
- **把「取货为空」与「加购为空」合成一组取值。** 少一组、少一个概念。代价是
  `report_not_ready`（这份报告还没确认）会被塞进「商城」那一组，而它与商城毫无关系 ——
  患者会去等一个不会发生的事（商城侧什么都没坏）。

## 后果

更容易的：

- 「一个客户端能产生、服务端产生不了的原因」不再存在：原因词表的一处改动不会漏掉浏览器
  里的第四份（一条跨语言断言钉住「患者侧可用取值 ⊆ 服务端出域取值」）。
- 归因不再依赖「服务端那句话里有没有 3 位数字」：`detail` 措辞变化不再翻转归因。
- 加购失败有两种不同的话术；报告读不到时患者被指向报告列表/商城入口，而不是被告知
  「商城暂时不可用」而去等一个不会发生的事。

更难的、被限制了的：

- **可见行为变化三处**：① 会话失效的话术从「请重新登录」（指向一个不存在的页面）改为
  指向商城入口；② 404 报告打不开时不再说「商城暂时不可用」；③ 加购失败出现两种话术。
- **多了一个跨层约定：响应头 `X-Report-Access-Reason`。** 它必须与 `app/api/deps.py` 的
  常量、前端 `api.js` 的常量三处同名 —— 少了任何一处，患者侧就静默落到中性说法
  （有测试钉住两端）。
- **`parseError` 的返回类型变了**：从「一个字符串」变成「一个带 `status` 与
  `accessReason` 的 Error」。所有调用方必须用它的 `.message`；这是本记录触及的第一处。
- 商城侧商品可见性与标签映射数据本身不在本记录射程内：ADR-0005 的「标签数据到位后需复验」
  那条 QA 用例仍是未通过状态，不因本记录变绿。
