# 解读失败是一个有成因的结论

Status: Accepted

本仓 ADR **0011**。兑现 ADR-0006 结尾那句「The patient-facing 「请重新上传」 is
genuinely misleading for this class of failure, but that is a separate UX decision with
its own ticket」。

## Context

一次报告解读失败之后，患者看到的是**一句通用话术**：「报告智能解读失败，请重新上传
或稍后重试。」这句话由四处互不同步的判定分别产生，而患者只看得到其中一句。

四个已实测的事实决定了这次改动：

- **重试与否靠对文件名与自由文本做子串嗅探。** `_TRANSIENT_ERROR_MARKERS` 是 14 个
  子串，匹配的文本是 `f"{filename}: {error}"` —— **文件名在被匹配的文本里**。一份
  「没抽出指标」的体检单改名成 `timeout.jpg` 就会被重跑三次；而真正瞬时的故障
  （额度耗尽 `insufficient_quota`、限流）因为用词不在表里而**一次都不重试**。
- **库把「当时查不了错」当成「这份报告读不出来」。** 解析路径的兜底把**任何**异常
  （数据库断连、目录不可用）包成 `ParsedReport(success=False)`，与「这份报告本来就没
  读出指标」汇成同一条路，最后都落 `failed` + 「请重新上传」。这正是 2026-10-10 那次
  「线上全部报告解读失败」事故（ADR-0006）对患者呈现的形状。
- **成因不出域。** `parsed_content["error_class"]` 写入后全仓无人读；
  `ReportExtractionJob.error_class` 经契约出域却没有任何前端读者；可重试性是一个
  布尔，前端根本拿不到。
- **兜底文案四层各写一遍**，措辞已经分叉（「请重试」vs「请重新上传或稍后重试。」vs
  「解析失败」），而「重新上传」是唯一被给出的动作 —— 它对多类失败是错的：同一份
  材料再传一遍既救不了「内容读不出来」，也救不了「服务当时不可用」，还会留下第二份记录。

## Decision

**「解读失败」是一个服务端拥有的领域概念：一次报告解读未能产出结构化指标时的唯一
成因结论，以及由它派生的两个决定。**

1. **五个成因，按坏在哪一环。** 判定入口是 `app/service/interpretation_failure.py`
   的 `classify(layer, exc, text=...)`，词表是 `FAILURES_ORDERED`：

   | 成因 | 坏在哪 | 可自动重试 | 患者动作 |
   | --- | --- | --- | --- |
   | `material_unreadable` | 报告原文读不出来（存的字节没了、渲染不了、类型走不通） | 否 | 重新上传 |
   | `service_unavailable` | 服务端自己读写出错（数据库、目录、内部逻辑） | **是** | 无需操作 |
   | `provider_rejected` | 模型拒绝了我们的请求（凭据、请求本身不合格） | 否 | 无需操作 |
   | `provider_unavailable` | 模型当时不可用（限流、额度、超时、协议错） | **是** | 无需操作 |
   | `content_unrecognized` | 报告原文里没有可确认的指标 | 否 | 换一份重传 |

   「可自动重试」与「患者动作」是成因的**派生读法**（`is_retryable` /
   `patient_action`），不是各自独立的事实。只有两个成因会请患者动手，而它们是两件
   不同的事：`material_unreadable` 是「你给的那份我们没读到」，`content_unrecognized`
   是「你给的这份读不出来」。

2. **判定优先看结构化事实，拿不到结构化事实才看文本，且给出的仍是具名成因。**
   `classify` 依次看 HTTP 状态码、异常类名（跨库没有共同基类，类名是唯一的结构化
   抓手）、最后才是文本用词。**文件名从不参与判定** —— 它今天在被嗅探的文本里。

3. **`layer` 由调用点给出，不由文本反推。** 调用点知道自己在调谁：读我们存的字节是
   `material`，读数据库是 `service`，调模型是 `provider`。一次数据库断连的错误文本里
   恰好写着什么，与它是不是基础设施故障无关。

4. **「内容里没有可确认的指标」不由文本判定，由抽取方当场判定。** 模型答上了、
   JSON 解析通过、结构合格，只是那一页没有指标 —— 那是**内容**事实
   （`content_unrecognized`），不是模型故障。把它降级成文本嗅探正是本 ADR 要消灭的
   错法。反过来，「一页都没抽到指标」而**有**页面报错时，成因取那些报错里**最上游**
   的那一环（`report_failure`，上游序 `FAILURES_ORDERED`）。

5. **报告的终态由队列决定，解析路径不落终态。** `_parse_report` 交出
   `ParseOutcome(succeeded, failure)`，`report_worker` 据 `failure` 决定重排队还是落
   `failed`。一次还会被重试的失败不该先给患者看一眼「解读失败」。

6. **重试只在确认之前有意义。** 一次重试会把已解析的指标行**全部删掉重插为
   `pending`**——患者核对过的行会连同他的表态一起消失。报告离开 `processing` 之后
   一律不再重试。此前这条路径会调 `transition(report, "processing")`，而
   `confirmed → processing` 不在迁移表里，于是 `IllegalTransition` 从 `run_next_job`
   抛出去，**worker 直接死掉**。

7. **成因逐报告出域，取代 `processing_error` / `processing_warnings` /
   `extraction_job.error_class` 三处半成品**（本系列第二张票）；患者侧只做映射，
   五类成因渲染成五句不同的话，也只有成因词表能产生「重新上传」这句话（第三张票）。

## Alternatives considered

- **把误判的真瞬时故障（`insufficient_quota`、限流）加进 `_TRANSIENT_ERROR_MARKERS`。**
  这是最小改动，也确实是「表里缺了几个词」这一层的正解。它输在只修了表里的**漏词**，
  没修**判据是文本巧合**这件事：改一个文件名仍然能翻转重试决策，而「再补几个词」是
  一个永远追不上的动作 —— 下一个 provider 换一个错误措辞，判定就又错了。收敛到一个
  具名成因之后，「漏词」不再是一个会导致错误行为的类别。

- **把 401/403 也变成可重试。** ADR-0006 已明确否决（「retrying with the same bad
  credential is futile; the fix is to not produce a 401」），本 ADR 同意该结论 ——
  它只改患者侧话术：凭据类失败不该叫患者重传。

- **保留 `processing_error` 与 `processing_warnings` 一段时间作为兼容读法。** 改动更
  小、可回滚，代价是「一次失败为什么失败」在契约里同时有两个答案，而四层各写文案的
  老路仍然活着 —— 这一 PRD 存在的理由就是那个多答案状态。

- **让失败块同时读队列状态，明说「已经自动重试 N 次仍未成功」。** 更透明，但成因就
  不再是唯一输入。次数由 `extraction_job.attempt_count`（现成字段）在**正在重试**的
  实时提示里给出；终态的话术不承诺「马上会自动重试」。

- **把「报告里没有可确认的指标」判成可重试。** 同一份材料再解析一遍，抽出来的还是
  同一批东西。患者能做的只有换一份更清晰的 —— 那就是 `upload_again` 而不是自动重试。

- **不改，只让患者侧的兜底文案更谨慎。** 这是本 ADR 最容易走上的岔路：文案改好了，
  患者仍然会为一次基础设施故障收到「请重新上传」，而可重试性仍然拿不到。文案是结论
  的最后一段路，不是结论本身。

## Consequences

更容易的：

- 改一个文件名不再翻转重试决策；真正的额度耗尽与限流开始被重试。
- 四层（worker 日志、审计事件、响应契约、患者文案）说的是同一个名字，排障不必再把
  三套词对齐。
- 新增一类失败会在契约层被**要求取名字**（词表是一个 `Literal`），而不是在第三个 JSON
  键里再塞一个字符串。
- 一次基础设施故障不再对患者表现为「这份报告读不出来」。

更难的、被限制了的：

- **一次失败的重试次数会变**：文件名巧合不再翻转判定，真瞬时故障开始重试。前端那句
  「第 N 次尝试」在患者眼里会比以前更常出现。
- **`_parse_report` 不再自己落终态**，报告的终态与「这一轮解析的结论」是两件事。读
  代码的人必须知道状态由队列收口，不能只看 `_parse_report`。
- **`layer` 是调用点的义务**：新的 provider 调用点若忘了给对 `layer`，成因就会归错环
  节。词表模块无法替它知道自己在调谁。
- **`provider_unavailable` 是 provider 环的兜底**：判不出来的 provider 故障一律归它，
  也就是一律**可重试**，只由 `REPORT_JOB_MAX_ATTEMPTS` 兜住上限。取这个方向是有意的
  —— 一个读不出来的 provider 故障**不是患者的输入的问题**，而叫患者重传是更坏的错。
- 历史行的 `parsed_content` 里没有 `failure` 键，读路径必须容得下（由后续票的契约读法
  处理）。

### 独立评审找出的四条（同一次改动内修掉）

第一版提交被独立评审（Devin）驳了四条，**四条都成立**，而且都是这次改动自己引入的。
记在这里而不是只留在 PR 里，因为它们各自是一条**边界**，不是四个笔误：

1. **成因与「有没有别的页成功了」是两件事。** 第一版写成
   `None if metrics else ...`，于是「一页超时、另一页正常」——最常见的失败形状——
   拿不到成因，队列据此判「不可重试」，超时那一页永远不会被再试一次。**成因是报告级的
   结论**，不因为别的页成功了就消失。
2. **记事实这一步自己也会失败。** 兜底分支把结论算出来之后去落库，而数据库都没了，
   `db.get` 原样再抛 —— 异常从 `run_next_job` 逃出去，worker 主循环结束：一次数据库
   抖动变成一条永久停摆的队列。**结论不依赖落库**，所以那一段只记日志。
3. **重试守卫必须在解析**之前**。** `_parse_report` 的第一件事就是删掉全部指标行重插为
   `pending`；把守卫放在重试分支里，患者核对过的行连同他的表态已经没了才被拦下。同一
   形状在 `recover_stale_jobs` 里也是这么处置的（报告已离开 `processing` 就 ack 任务）。
4. **只印在消息里的状态码也是结构化事实。** `classify` 拿不到异常属性上的状态码时，
   文本是唯一剩下的判据 —— 调用点不把 `str(exc)` 交出去，一条**凭据过期**就会被判成
   可重试，同一份无效凭据被重发 `REPORT_JOB_MAX_ATTEMPTS` 次（ADR-0006 明确否决过）。

共同点：**四条都把「某个字段有值」当成了「这件事没发生」** —— 有指标就当没有失败、开了
session 就当库里还在、报告存在就当它还在我们手上、有异常对象就当状态码拿得到。这一条
比四条本身更值得记住。
