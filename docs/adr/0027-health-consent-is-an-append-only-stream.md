# 27. 健康数据同意是一条只追加的记录流，门槛读同一次判定

日期：2026-10-27
Status: Accepted

本仓 ADR **0027**。它落地 [[0026]] 第 5 条在 health-flow 这一侧的具体形状；0026 仍然
有效，本记录不改变它的任何结论，只回答「同意在数据里长什么样、门槛读哪一次判定」。

## Context

ADR 0026 把「健康数据同意」定为服务端持有的领域概念：两项彼此独立（报告解读必选、商品
推荐可选）、记录只追加、文本版本一变旧同意即失效、门槛在上传与推荐两处执行。它没有说
**记录是什么形状**、**「当前是否有效」由谁算**、以及**上传闸门与状态接口是不是两份判据**。

这三件事各自都有一个走上去很自然的错误答案，而三种错误都在本仓有先例：

- 把「当前是否同意」存成一个布尔字段或一行可更新的状态。它足以让界面工作，但**举不了
  证**：患者何时同意、对哪一版文本、从哪个通道表的态都没有了，而这三样正是合规要问的。
  本仓的审计事件（[[0016]]）已经付过一次「记录被改写就不是证据」的学费。
- 让客户端在请求里带文本版本。看起来更「显式」，实际是让客户端声称自己对一版从未展示过的
  文本表过态。
- 状态接口自己比一次版本号、上传闸门再比一次。两个版本号各比一次就是两条会漂移的判据，
  而这条概念最坏的失败形状正是「界面说已同意、服务端拒绝上传」。

## Decision

1. **记录只追加，一行一条表态。** `health_data_consents` 的每一行是（主体、同意项、
   表态、文本版本、时间、来源）；**代码里没有 UPDATE 与 DELETE 的路径**。撤回是又一条
   `revoked` 行，不是删掉上一条。文本版本是**表态那一刻**服务端要求的版本，原样留着，
   所以一行同时回答「当时他对哪一版表的态」与（配合当前配置）「现在还算不算数」。

2. **当前状态是那份记录的一次投影，取每项最新一条。** 最新一条决定一切，**包括它写在
   旧版本上**——不是「最近一条有效版本的记录」。后者会让「他在新版本文本下撤回过」被一条
   更早的旧版同意悄悄盖过去。

3. **有效 = 最新一条是 `granted` 且它的 `text_version` 等于当前要求的版本。** 这个判据
   只有一处（`ConsentState.valid`），状态接口渲染它，上传闸门读它。两处不是两份判据，
   是同一次判定。

4. **文本版本由服务端写定，两项各自一个配置项。** 请求里没有版本字段。两项分开是刻意的：
   法务改一版「报告解读」的文本不该顺带作废患者对「商品推荐」的表态。

5. **来源由会话通道判定，不由客户端声明。** 带 `Authorization: Bearer` 的是商城 H5，
   否则是旧前端；测试夹具代主体预置的表态有自己的 `seed` 来源。判据与
   `request_session_token` 同形，所以「令牌从哪来」与「这次表态度从哪来」不会给出两个
   互相矛盾的答案。

6. **闸门在读取任何文件之前，拒绝的成因进 `REPORT_ACCESS_REASONS_ORDERED`。** 没有有效
   解读同意时上传返回 403，原因 `report_interpretation_consent_required` 经
   `X-Report-Access-Reason` 出域（ADR 0018 的具名归因、ADR 0019 的单一所有者）。它是
   **报告级访问问题**，不是「取货为空」——患者侧的动作是去完成授权，不是稍后重试。
   判定被问的是**这份报告将来的 owner**（`resolve_owner`），与会话主体无关的通道不参与。

## 被否掉的替代形态

**一行可更新的「当前同意」状态（或在主体行上加两个布尔列）。**
最强的理由：读状态与判闸门都变成一次单行读取，没有「最新一条」这种排序问题，也没有
「旧版本上的表态」这种边界；对一个只要界面正确的实现，这是最少的代码。

它输在**举证**。合规要回答的是「他何时、对哪一版、通过哪个通道同意了」，而可更新的行
只记得最后一次。更具体的一处损失是撤回：删掉或覆盖上一条之后，「他曾经同意过、后来撤回」
从记录里消失，只剩「现在没同意」。本仓在审计事件上已经判定过同一件事——改历史记录是编辑
记录，不是描述记录（[[0016]]）。

**客户端在请求里带 `text_version`。**
最强的理由：它把「患者表的是对哪一版的态度」写成请求的一部分，服务端不必信赖自己那一刻
的配置，也便于离线补录。

它输在**它可以撒谎**。版本号是患者看到的文本的身份，只有展示那一版的服务端知道它是什么；
让客户端带一个，等于允许它声称对一版从未展示过的文本表过态。补录这一需求可以用
`source` 表达，不需要把判据交给调用方。

**单独建一个「同意服务」或一张把两项合在一起的主体级同意行。**
最强的理由：同意看起来是「账号级」的事实，两项合成一行能让「这个主体同意情况如何」一次
读完，也便于将来加第三项时集中处理。

它输在**两项是独立的**。合成一行就要在行内再分两组字段与两个版本号，或者每次只改一项时
重写整行——前者是两条会漂移的判据换了位置，后者违反只追加。逐项一行让「撤回推荐不影响
报告解读」成为数据结构本身的性质，而不是一条要记得去遵守的规则。

**闸门放在上传接口的依赖层（一个 `Depends`），或只在 `/api/auth/consent` 上执行。**
最强的理由：依赖层复用得最干净，将来推荐接口加闸门时可以直接套同一个依赖；只在状态接口
执行则把门槛留在界面里。

它输在两处。其一，只在状态接口执行等于没有门槛——这正是 PRD 点名要消灭的「门槛只存在于
界面上」。其二，依赖层的拒绝发生在读取请求体**之前**的位置之外：上传是 multipart，依赖在
文件被接收之后才跑，于是「没有同意」会表现为「格式不对」或一次白收的字节。所以闸门是
路由函数体的第一句。

## Consequences

**更容易的：**

- 「他同意过什么、什么时候、对哪一版、从哪个通道」是一串可读的行，不需要另一份审计。
- 状态接口与上传闸门不可能各说各话：同一个 `ConsentState.valid` 同时回答两个问题。
- 文本版本更新只是一次配置改动：闸门与状态读取同时失效，不涉及任何数据迁移。
- 撤回（下一张单）不需要新增「状态」表：它的留证就是它自己那一行。

**更难的、被限制了的：**

- **这张表只增不减。** 主体注销或按删除请求清理时，同意记录不能被当作「他的数据」一并删掉
  —— 它是同意发生过这件事的证明。这需要一条明确的保留策略，本记录只把它写下来。
- **「最新」按自增 `id` 判，不按时间戳。** 同一秒内的两条记录靠时间戳分不出先后；把判据
  放在时间戳上会让一次快速的重试产生不确定的当前状态。代价是这条判据依赖单库自增。
- **文本版本是一个字符串，不是外键。** 它没有指向任何「文本表」——文本由法务提供、存在
  业务侧。代价是拼错一个版本号会让所有既有同意静默失效（方向是安全的：失效要求重新同意，
  不是放行）。
- **上传闸门问的是将来的 owner，不是会话主体。** 两者今天相等（`resolve_owner` 的账户
  分支取的就是会话主体），但一个还没有主体的请求（无主哨兵）因此落 403 —— 没主体就无从
  同意，fail closed。将来若有第三种主体通道，它必须自己回答「谁同意了」。

## 未做的

- 推荐接口上的「商品推荐」闸门（下一张单）：本记录只把那一项**存**下来，不执行。
- 撤回解读同意时删除该主体全部报告（下一张单）：本记录不写删除路径。
- 同意界面与二次确认：在商城 H5 模块里，不在本仓。
- 同意文本本身：由法务提供，本记录只承载它的**版本号**。
