# 28. 商品推荐的同意闸门与按健康问题分组：一次取货，分组由本仓判定归属

日期：2026-10-27
Status: Accepted

本仓 ADR **0028**。它落地 [[0026]] 第 5 条里「推荐以另行同意为前提」那半句，并给
「推荐商品」加了一个新的出域形状（`groups`）。[[0018]]（取货为空的原因由服务端具名）
与 [[0005]]（商品由服务端读取）都仍然有效；本记录不改它们的结论，只回答两件事：
**闸门放在哪一层**、**分组凭什么判定一件商品属于哪个健康问题**。

## Context

到 #271 为止，推荐端点是这样一条链：读报告 → 从 `evidence_result.findings` 取已确认的
健康问题 → 把每个问题映射成商城标签 → **一次**并集取货 → 出域一个扁平的 `items` 与
一个整体 `reason`。

两件事此前没落地。

其一，**「商品推荐」这项同意只被存下来了，没有被执行**（[[0027]] 的「未做的」里点名）。
它的另一项「报告解读」在上传路上已经是 403 闸门，而推荐这一项没有任何服务端判定：
患者没勾选，推荐照样给出。这正是 PRD 点名的「门槛不只存在于界面上」的反面。

其二，**响应回答不了「这件商品和哪项发现有关」**。患者要的是「针对血脂偏高」这样的
分组，而扁平的 `items` 把两个健康方向的商品堆在一起。分组不是排版偏好：商城侧的商品
详情页要带一块「为什么推荐」（来自哪份报告、哪项指标、第几页），而那句解释的前提是
「这件商品属于哪个健康问题」——它必须由服务端给出，不能让商城或患者侧去猜。

分组还有一颗具体的钉子：**商城不告诉我们归属。** 商品列表/批量接口不返回
`goodsSpuLabelList`（ADR 0005 的 2026-09-30 修订实测过，恒为 `null`），而按标签取货的
接口回应的是一个**命中集合**，不带「这条命中了哪个标签」。所以「拿一次并集结果按商品
反查方向」这条路没有可用的判据。

## Decision

1. **闸门在调用商城之前，读的是与状态接口同一次判定。**
   推荐端点先判 `consent.has_valid(db, 主体, "product_recommendation")`，不成立就返回
   **200**、空 `items` / 空 `groups`、`reason = "product_recommendation_consent_required"`，
   **一次商城请求都不发**。

   200 而不是 403：推荐是报告页的一个区块，不是一次会被「拒绝」的访问。403 会把
   「没开启推荐」渲染成一个错误，而患者手里有一个能解决它的动作（去开启）。这一点与
   上传闸门不同 —— 上传是那一次**写**操作的准入，拒绝就是拒绝。

   闸门**先于**「这份报告有没有健康风险」：报告有没有风险是同意之后才谈得上的事，
   反过来会让一个没同意的患者读到「本次未能生成健康风险提示」，去找报告的问题。

2. **新取值只住在「取货为空」那一组，不进商城模块的子集。**
   `product_recommendation_consent_required` 加进
   `RECOMMENDATION_REASONS_ORDERED`（[[0019]] 的单一所有者），但**不**加进
   `MALL_GOODS_REASONS_ORDERED`：`fetch_goods` 永远不会返回它，而闸门恰恰在它之前。
   把它并进商城那一组，会让「哪一层能产生这个取值」这件事在类型上失真。
   同时它也不复用「报告访问失败」那一组的 `report_interpretation_consent_required`
   —— 那是「这次请求连报告都读不到」的报告级问题，而这里报告照常可读，只是没有推荐。

3. **按健康问题逐组取货，隶属关系由那一次取货本身给出。**
   对每个**有标签映射**的健康问题各问一次商城（`label_pairs_for` + 按标签取货），
   那一次的命中集合就是该组的商品。归属因此不是推出来的，是商城按我们发出去的那一对
   标签回答的。

   代价是 N 次商城调用（N 是有映射的健康方向数，一份报告通常一两个）。换来的是分组
   不是装饰，且**不需要第二份商品-方向对应表** —— 那会是商城数据在本仓的副本，与
   ADR 0005 拒绝镜像商品目录同一个理由。

   没有映射的健康方向**不发出取货**，它的组如实说 `no_label_data`：患者看到的是
   「该方向暂无可推荐商品」，而「我们还没建映射」是内部事实。

4. **一件商品只归一组，按健康问题的出现顺序先到先得。**
   同一件商品可能同时挂两个方向的标签，于是出现在两次命中集合里。把它在两处各展示
   一遍是重复推荐；把它从后一组里悄悄抹掉又不说明，会让后一组看起来「没货」。所以
   组序（即报告里健康问题的出现顺序）决定归属，先被认领的商品不再出现在后面的组里，
   而它**一定**出现在扁平的 `items` 里。

5. **组的原因为空时用 `no_label_data`；商城整体不可达时每组都带 `mall_unavailable`。**
   前者是「这一组没货」，后者是「这一次取货没成」——把后者写进某一组，会让患者把
   商城故障读成「这个方向没有商品」。

6. **扁平 `items` / `reason` 保持不变，与新 `groups` 同时出域。**
   旧前端继续可用，一字不改（它只多了一行「未同意」的文案映射）。`items` 是各组商品
   的并集（按首次出现去重），整体原因保持改动前的口径：有货则空；没货时只要商城可达
   就是 `no_label_data`，全部不可达才是 `mall_unavailable`。`items` 在旧前端退役时删除，
   另建单（PRD #266 的退役步骤）。

## 被否掉的替代形态

**一次并集取货，再按商品自带的 `labels` 做本地分组。**
最强的理由：它只有一次商城调用，而且复用 `filter_by_labels` 这个已经在跑的判据；
按 ADR 0005 的修订，商城端点「一旦补上该字段就自动生效」，所以它看起来是同一笔投资。
它输在**那个字段今天不存在，而分组的正确性不能等它**：商品列表/批量接口恒不返回
标签，这个形态下每组永远为空，且空得看起来像「商城没货」—— 一种只有读代码才能发现
的静默错误。加一个「字段缺失就退回单组」的兜底更糟：那会让分组在一份报告上生效、
在另一份上不生效，而患者看到的差别无从解释。

**让商城在按标签取货的响应里回显每条命中对应哪个标签。**
最强的理由：这是最干净的归属——由权威方在应答里说明，本仓一次调用、零猜测。
它输在**那是另一个仓库的改动**：商城侧接口今天没有这个字段，加上它要跨仓排期与
发布，而分组是 PRD 里患者可见的一项。本记录选择在自己的发布链里解决；该字段出现后
可以退回一次调用，那是未来的优化，不是今天的依赖。

**把闸门做成依赖（`Depends`）挂在推荐路由上。**
最强的理由：与 [[0027]] 里上传闸门「能不能放依赖层」的讨论同形——复用最干净，将来
再加一个闸门时是同一行。
它输在它买不到任何东西：推荐端点没有请求体，不在依赖里跑就能在函数体第一句跑，
而依赖层会把这个判定从「这条链路的一个步骤」变成「一个看不见的前置」。上传那边拒绝
依赖层有硬理由（multipart 在依赖之后才被接收），推荐这边没有，所以不为一致性而一致性。

**没有映射的健康方向也发一次取货（用空标签）。**
最强的理由：它能保证「每次都真的问了商城」，与 ADR 0005 里「无标签仍然照常调用商城」
那句字面一致。
它输在它是一次**无判据的取货**：空标签交给商城不会得到「这个方向的商品」，只会得到
一个未过滤的集合，而把它当成那一组的商品，就是把不相关商品推给患者——正是 ADR 0005
的 `filter_by_labels` 要防的事。那句「无标签也照常调用」说的是**至少有一个方向有映射**
的那条老路径，不是「一个映射都没有时也要发一次」。

**闸门返回 403，让患者侧把它当错误渲染。**
最强的理由：与上传闸门同一个 HTTP 形状，客户端处理「被拒绝」只需要一条分支。
它输在**语义**：上传是写入的准入，拒绝就是拒绝；推荐是读一个可选区块，没开启时的
正确表现是一个带指引的空态，不是一个错误横幅。把它做成 403 还会诱导客户端把它与
「会话失效」「报告不存在」放进同一条重试/登录分支，而那三件事的患者动作各不相同。

## Consequences

更容易的：

- **「没同意就不问商城」成为一个可断言的事实。** 它不是界面上的一个勾：HTTP 层的
  负控是 `fetch_goods` 一次都没被调用，而不是「响应看起来是空的」——「先问、再丢」
  的实现会返回同样的 JSON。
- **分组不需要维护清单。** 归属来自我们发出去的标签，商品增减、标签变化都不需要改
  `condition_tags` 之外的东西。
- **旧前端零改动。** 新形状是**增加**一个字段，`items` / `reason` 的取值与以前一致；
  唯一的改动是它多了「未同意」那一句文案（否则患者会看到兜底的那句话）。

更难的、被限制了的：

- **一次推荐现在是 N 次商城调用**（N 是有映射的健康方向数）。延迟从一次往返变成 N 次
  往返，超时也按次发生：一次超时只让那一组为空，不会让整份推荐为空——这是刻意的，
  但它意味着「部分组不可达」是一个正常状态，患者侧要按组读原因。
- **组序承担了一个语义。** 「先到先得」使分组的归属依赖健康问题在报告里的顺序，
  而这个顺序来自证据服务的 findings。改变排序会改变哪一组拿到那件共挂的商品。
- **`items` 与 `groups` 会暂时说同一件事两遍。** 在旧前端退役前，两形状同时出域，
  客户端读哪一个都能工作；代价是响应更大，且「只改一处」的诱惑存在。两者的关系
  （并集 / 子集）由测试钉住。
- **分组结论依赖 `condition_tags` 的覆盖。** 一个方向没建映射，它就没有商品可展示，
  而患者看到的是「暂无商品」——分组不会暴露「我们缺映射」这件事，它只在运维侧可见。
- **`groups` 没有为空报告（`no_published_card`）与未同意提供组。** 两种情况下 `groups`
  是空列表：没有健康问题就没有组，没有同意就没有取货。患者侧的指引来自顶层 `reason`。

## 未做的

- 删除扁平的 `items`：属于旧前端退役，另建单（PRD #266）。
- 商城侧「为什么推荐」块：在商城 H5 模块里做，本仓只提供 `groups` 与报告详情接口。
- 按商品名称过滤：PRD 明确不做。
- 撤回「商品推荐」同意后的任何数据动作：推荐同意是可选的，撤回只停止推荐，报告保留
  （PRD #266）；撤回「报告解读」时删除全部报告是下一张单。
- 让商城在按标签取货的响应里回显命中标签：本记录依赖了「它今天不回显」，将来它若回显，
  可以退回一次调用。
