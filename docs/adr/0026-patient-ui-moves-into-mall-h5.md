# 26. 患者界面并入商城 H5：本仓只提供跨源 API（Bearer 会话、跨源白名单），并在服务端执行健康数据同意

日期：2026-10-27
Status: Accepted

本仓 ADR **0026**。跨仓关系：同一次方向变更也要求 genesis-evidence 的 ADR 0019 在
「入口形态」一节被部分取代（入口由患者门户改为 API 入口）；**那一侧的记录在 genesis-evidence
仓库里单独写**，本记录只描述 health-flow 这一侧的形态变化，不复述对方的措辞。

## Context

患者要用的「体检报告解读与健康风险提示」今天是另一条路：在商城里点一个入口，带着一次性
票据**跳转**到另一个域名上的独立 React 前端。那个页面的界面、账号与购物都与商城割裂 ——
在商城里买东西要再跳回去，还可能再登录一次。这条跳转通道上线以来，运维观测到的真实患者
流量为**零**。

设计方交付的 40 页新界面预设功能**长在商城里**：从商城「我的」页进入，上传 → 核对 →
解读 → 建议 → 商品是一个闭环，推荐商品要能直接落进商城的原生商品详情与购物车。这不再是
「把现有页面搬个位置」：患者的整个旅程应当在一个源里完成。

与此同时有三件事从未落地：健康数据属于敏感个人信息，需要可追溯的**单独同意**；患者撤回
同意后数据要能删除；推荐商品也须以患者**另行**同意为前提。这三件事都不是在页面上加一段
说明能满足的 —— 门槛要成立，就必须由服务端记录并强制执行，否则它只是一个界面。

本决定同时改变了本仓的网络暴露面：此前浏览器只与页面自身的源通信，此后商城 H5 要跨源
调用本仓的接口。暴露面的变化需要一条可审计的记录，这就是这一节的来源。

## Decision

**患者界面迁出本仓，成为商城 H5 里的一个模块；本仓退化为纯 API 后端。**

1. **界面归商城，数据归本仓。** 报告服务的界面、导航、上传与核对交互都在商城 H5 的模块
   里实现，沿用商城账号；本仓只保留 HTTP API。genesis-evidence 的证据 API 不变，仍只被
   本仓内部调用。

2. **会话从「浏览器 Cookie」扩展为「Bearer 令牌」。** 票据兑换接口除照常写 Cookie 外，
   在响应体里返回会话令牌与过期时刻；会话解析同时接受 `Authorization: Bearer`。Bearer 与
   Cookie 指向**同一条服务端会话行**，因此都可吊销，退出登录对两者同样生效。**两种形态的
   有效期都是 12 小时**（同一条行只有一个寿命；旧通道此前是 30 天，现在一并收到 12 小时，
   不维护第二种）。「令牌从哪读」只有一个入口：先看 `Authorization: Bearer`，再看 Cookie。
   Cookie 路径在旧前端退役时删除。

3. **跨源放行是一次暴露变更，按最小面放行。** 允许的源**由配置注入**，不写死在代码里，
   只包含商城 H5 的生产源；`allow_credentials=false`（不带凭据）；允许的请求头显式列为
   `Authorization` 与 `Content-Type`，不再用 `*`；暴露报告访问失败原因头
   `X-Report-Access-Reason`。最后一条不是便利，是**必需**：不暴露的话，跨源的前端读不到
   那个头，「会话失效」与「报告不存在」就无法区分，ADR 0018 建立的具名归因会退回猜文本。

4. **会话失效由客户端静默续期，不再直接赶人去登录。** 收到 401 且具名原因是会话失效时，
   客户端先用商城会话换一次新令牌并重试；仍然失败才去商城登录。具名成因仍由服务端判定
   并出域（ADR 0018 的结论不变，改变的只是患者侧对它的动作）。

5. **「健康数据同意」是一个新的服务端领域概念。** 两项彼此独立的同意：**报告解读**（必选）
   与**商品推荐**（可选，默认不勾）。记录**只追加**，当前状态取每项最新一条；当前要求的
   文本版本由配置给出，文本版本一变，此前的同意即不再有效。**门槛在服务端执行**：没有对
   当前版本的有效解读同意，上传返回 403 并给出具名原因；没有有效推荐同意，推荐返回
   「未同意」且**不调用商城**；撤回解读同意时删除该主体的全部报告。词汇定义见
   `GLOSSARY.md` 的「健康数据同意」。

6. **退役是两步，回退路径不丢。** 商城发布新模块、入口改指模块之后，旧的独立前端与 Cookie
   会话保留两周观测流量；「切流」与「退役」分开。退役后公开入口只提供 API。回退方式是
   由商城团队重新发布上一版商城 H5 —— 本仓不回退到旧前端形态。

7. **ADR 0005 仍然有效。** 「商品由本仓服务端读取商城、浏览器不直接调商城」这条决定没有
   改变，改变的只是它那句「前端只与自身同源通信」的**前提**：患者界面现在在另一个源上。
   0005 的正文已就地加注指向本记录，避免两条 Accepted 记录互相矛盾。

## 被否掉的替代形态

### 跳转通道（现状）

最强的理由：它**已经在跑**，而且形态是对的 —— 页面与 API 同源，没有跨源暴露，没有第二种
会话形态，票据兑换那一条链路已经解决了「商城说他是谁」。把它留下，只需要继续维护那一份
前端。

它输在三处。其一，实测的真实患者流量是**零** —— 一条没人走的通道，维护成本照付，却没人
从中得到价值。其二，它的割裂是结构性的，不是文案能修的：账号要再来一次，购物要跳回商城，
而设计要求商品从解读结果直接落进商城购物车 —— 在两个源之间，这条闭环要靠深链一跳一跳地
拼。其三，它把患者界面钉在了一个只有本仓维护的构建里，商城侧的改版永远追不上它。所以它
不是被「更好的实现」取代，而是被**患者旅程换了一个家**取代。

### 经商城后端代理

最强的理由：这是**暴露面最小**的一种 —— 浏览器只与商城自己的源通信，本仓可以完全不出现在
公网，不需要跨源白名单，Bearer 令牌也不必交给浏览器；身份与租户由商城后端在代理时注入，
本仓甚至不必改会话形态。

它输在职责与节奏。代理把本仓的每个接口、每个字段都变成一次**两仓的**变更：商城后端要加
一条转发路径、跟着本仓的契约改、走自己的发布窗口，而这条路径承载的是健康数据 —— 一个
商城后端没有理由经手的流量。更关键的是，患者界面的归属已经明确在商城 H5（模块代码由我方
写、由商城团队评审合并），再在中间加一层我们无法直接修改的后端，等于把「我方负责的实现」
拆成两半，而其中一半不在我方的发布链上。白名单加 Bearer 把这条边界的代价留在了本仓内部，
这是可评审的。

### 移植进商城后端

最强的理由：一个源、一次部署、一个团队。跨源、令牌、白名单、两套会话形态全部消失；报告
存储和接口跟着界面走，不可能漂移。对一个只看这张图的人来说，这是最干净的形态。

它输在**它搬的东西不是页面**。报告解析、证据匹配、已发布知识卡的准入判定、报告存储与
原件保留策略，是一整套带独立契约的服务，且已经在本仓、用本仓的测试与 ADR 守着。把它们
移植进一个由别的团队治理的代码库，等于把医疗解读的判定权交给一个不承担它的地方；而本仓
的每一条领域不变式（计数由服务端算、准入结论具名、失败成因具名）都要跟着重写一遍，且失去
本仓的守卫。界面搬走是没问题的；**判定不能跟着界面走**。这也是商城原有那套健康功能分包
与新模块并存、互不复用的原因：并存的代价小于合并的代价。

### 跨源但沿用凭据 Cookie（`allow_credentials=true`）

最强的理由：复用已经在用的 HttpOnly 会话 Cookie，浏览器自动携带，前端一行令牌代码都不用
写，也不用把令牌交给 JavaScript —— 从「令牌被 XSS 读走」的角度看，这比 Bearer 更安全。

它输在三条具体的要求上。其一，跨源的凭据 Cookie 需要 `SameSite=None` 与第三方 Cookie 的
放行，而这是微信内置浏览器里最不可控的一环，一个被拦下的 Cookie 表现为「莫名被登出」。
其二，共用一部手机的场景要求「切换商城账号后模块不再显示上一位用户的报告」，以及「关闭
微信页面后令牌随之失效」—— 这两条都需要模块在**每次进入**时拿令牌与商城当前用户比对，
并能在页面关闭时丢弃它；Cookie 既不能读、也不会随页面关闭而消失。其三，把 Cookie 暴露给
跨源，意味着跨源白名单一旦配错，暴露的就不只是一个令牌，而是浏览器会**自动**带上的凭据。
所以选择 Bearer 加 `allow_credentials=false`：令牌由模块显式持有、显式比对、显式丢弃，
暴露面是一个可撤销的字符串，而不是一个会被自动附上的会话。

## Consequences

### 更容易的

- **患者只走一条路。** 入口、「我的」、商品详情、购物车、下单都在商城里，不需要第二次
  登录，也没有「跳回去」这一步。
- **本仓的对外面收窄成 API。** 独立前端、它的构建与前端部署随退役一起消失；公开入口只剩
  真正被用到的部分。界面迭代不再需要本仓发版。
- **同意成为一个可举证的服务端事实。** 每一次同意与撤回都有只追加的记录（主体、同意项、
  表态、文本版本、时间、来源），且门槛在上传与推荐两处真的执行 —— 而不是界面上一个勾。
- **会话只有一种存储形态。** Bearer 与 Cookie 指向同一条会话行，吊销、过期、主体解析都
  只有一套判据。令牌的读取收敛在一个入口（`request_session_token`），所以「退出登录对
  Bearer 不生效」这类缺陷没有第二种形状可以藏。

### 更难的、被限制了的

- **跨源白名单成为一处安全相关的配置。** 源列表由配置注入是刻意的（可审计、可随商城域名
  调整），代价是配错的后果比配错一行代码更直接：多一个源就是多一个能带令牌访问患者报告的
  页面。它必须被当成发布检查项，不是普通环境变量。
- **令牌落在 `sessionStorage`，能被同源的脚本读到。** 这是 Bearer 换来的代价：商城 H5 里
  的一段 XSS 可以读走令牌。缓解是三件事同时成立 —— 令牌 12 小时过期且可吊销、只对应一个
  主体、页面关闭即丢弃；但这不是零风险，是**接受了的**风险。
- **契约变更变成跨仓变更。** 本仓改一个响应字段，商城 H5 要跟着发一版；模块的所有权在
  商城团队，不在本仓的发布链上。此前的同源前端可以随本仓一起发，这一条不再成立。
- **旧前端在退役前会先坏掉。** 同意门槛一旦上线，没有同意页的旧前端就无法上传。这是有意
  接受的：旧通道没有真实患者，且它本来就要退役；「先切流、后退役」的顺序保证回退路径在
  观察期内仍然可用。
- **观察期是流程，不是代码。** 「新模块上线后旧前端再保留两周」写在发布步骤里，没有任何
  机制会因为提前退役而变红；它依赖发布负责人按步骤执行。
- **`X-Report-Access-Reason` 的暴露是跨源前提。** 它同时是三处同名的跨层约定（服务端常量、
  响应头、患者侧读取）。不暴露它，跨源的前端就静默退回中性说法 —— 症状与 ADR 0018 要消灭
  的那一种相同，只是换了一层。

## 未做的

- 商城 H5 模块本身的实现、商城侧改版、黄主题配置：在商城代码库与另一条发布链上，不在本
  记录射程内。
- 旧前端的删除、Cookie 会话路径的删除、票据跳转入口页的退役：属于退役步骤，在观察期之后。
- genesis-evidence 侧的入口形态记录：另仓单独记录。
